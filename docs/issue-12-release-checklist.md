## 反映順

1. PRのCI（フロント・PHP・MySQL）が成功していることを確認する。
2. DBと現在のAPI・フロント・非公開設定をバックアップする。
3. `database/migrations/005_add_mutation_receipts.sql` を実行する。
   既存DBへの追加テーブルで、支払いデータは変更しない。初期SQLだけではこの追加テーブルは作られない。
4. `docs/sakura-cloud-setup.md` のセッション設定と実行環境による上書きを確認する。
5. 新APIを先に配置し、その後フロントの `dist/` を配置する。
6. 古い画面を再読み込みしてService Worker更新を確認する。端末のゲスト・キャッシュ・未送信データは削除しない。
7. 以下の表を確認し、配備したコミット／日時・端末／OS・結果をIssue #10へ記録する。

旧フロントのまとまり全件を指定するアーカイブ要求は、新APIでは拒否される。
誤って対象を増やすことを防ぐための変更なので、旧画面から処理できない場合は新しい画面へ更新する。
既存の未送信キューは保持する。旧キューで版番号・処理対象IDが不足している操作は、競合解決画面から
サーバーの内容へ戻して、対象を確認して操作し直す。

## ロールバック

API・フロントを一緒に旧版へ戻す。`mutation_receipts` は残し、削除・全件消去しない。
削除すると、同じ操作を後から再送した端末へ成功済みの応答を返せなくなる。
旧版へ戻すと今回防いだ競合・誤削除の挙動も戻るため、データ変更が必要な復旧はバックアップと現状を確認してから行う。
